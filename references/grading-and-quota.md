# A/B/C 分级与投递配置：判据与依据

> 这份文件回答「为什么这样分、比例怎么定、换行业怎么配」。机制与命令在 SKILL.md 的
> 「A/B 分级与投递顺序」一节；本文件是决策依据，用户再次质疑分级或要给别人用时读这里。

## 分级是身份，不是分数

分数只能排序，不能表达「这是哪一类岗」。一旦用 `scoring` 的加分项去表达类型，只要某城市的
加成 ≥ `a_min`，该城市**全部**岗位就自动进 A（实测上海加成 4 = a_min 4 → 415/424 判 A，
已投 163 条清一色 A，其中三成命中硬排除词）。

自检一条：`max(scoring.city_bonus.values()) < scoring.a_min` 必须成立，否则分级退化成
「按城市分级」。接手别人的配置时先跑这条。

## 平台侧 / 品牌侧：同名岗位不是同一类

同一个「城市经理」有两种完全不同的活：

| | 平台侧（A） | 品牌侧（B） |
|--|--|--|
| 管什么 | 商户、供给、开城、BD 团队 | 自家门店、加盟商、督导 |
| JD 信号 | 商户拓展、商家运营、新签商户、开城、城市代理、GMV、地推、平台政策、KA 商家、订单量 | 门店运营、加盟商、督导、店长、选址、装修、陈列、直营门店、库存 |

「美团城市经理」是平台侧，「华莱士城市经理」是品牌侧 —— 用户说 A 类时，指的是
**同职能 × 同一侧**，不是同行业。跟他确认分级标准时按这两个维度问，别按行业名问。

## 只用列表字段判级，两个方向都会错

- **宽判**（行业字段 + 大行业词）：连锁品牌的门店管理岗整类进 A。`brandIndustry` 是公司
  自报，网鱼写「互联网」、美妆连锁写「生活服务O2O」，字段本身不可靠。
- **严判**（只认平台业务词）：真平台岗被降级 —— 美团充电宝、货拉拉、转转、同程的城市经理
  标题里只有「城市经理」四个字，业务词全在 JD 里。

可靠做法是两段：列表阶段只筛职能（标 `A?`/`B?`，职能不命中的 C 直接丢），发送时读 JD 定终级。
注意「发送本来就要开详情页」只对**真要发的那几个**成立：一池 600+ 候选、每跳只发 4–8 个，
若把 C 也拿去读 JD，就变成每跳开六百多次详情页 —— 40 分钟预算当场打爆，访问频率也不像人。
所以主循环必须先用纯函数粗标筛一遍，再谈开页；同时用 `max_inspect_per_window` 封顶，
并给 `hidden_b_probe` 留几个名额，专门捞「行业写互联网、JD 写门店」的错标岗。
判级结果连同 JD 指纹缓存进 state，否则 22 点出总结时会重复开页。
**JD 被远端正悄悄改写是发现不了的**，这个限制要如实写在文档里，不要承诺实时准确。

## 配额：固定比例 > 兜底补位

先算存量：`可投 A 条数 ÷ 日额度 = 能撑几天`。存量不足 3 天时，「B 只在 A 不够时补位」等于
「第 N 天起 B 自动变成主力」—— 画像突变，风控特征和推荐画像都最差，而且不可预测。

固定比例（如 22A/8B）每天画像平稳、跨行样本按天累积，两周就能做分方向对比。
拿「跨行岗待遇低、不值得占配额」当理由之前先看分布：实测 B 类 ≥25K 的岗位比 A 类更多
（10 vs 6），可投存量也更大（71 vs 52）—— 直觉经常和数据反过来。

## 顺延公式

```
每级 quota = min(max_per_window, ceil(该级剩余额度 / 含当前的剩余窗口数))
本跳预算  = min(日剩余, max_per_window)
```

**两个数不是一回事，必须再压一次。** 上式是「每级」封顶，各级相加可以远超本跳预算；
`do_send` 先 A 后 B，A 配额 ≥ 预算时就把预算吃光，B 一条也发不出去（A8+B8 + 预算 8 → 全发成 A）。
压法是按 A:B 比例缩到预算内（`shrink_quotas`，最大余数法），同一场景变 4A4B。
验收时看 `by_grade` 分布，不能只看 `sent` 总数 —— 总数对了但全是 A，就是这个问题。

不记「跳过几次」：断网或未登录跳过的窗口自动摊到后面。`max_per_window` 是必须的，否则
连续失败后会在最后两跳各砸 8 个 —— 比每天稳定发更显眼。额度只在真发出后记账，失败不扣。

## 失败样本口径

- 只统计「明确说不合适」会系统性低估：这个平台上的多数失败是**已读不回**。
- 失败样本 = **明确拒绝 + 投递满 72h 无回复**，两类分开计数、都进分母。
- 每条必须标归属：`our_apply`（job_id ∈ state.sent）/ `hr_initiated` / `unknown`。
  只有 `our_apply` 能用来判断投放精准度，HR 主动找来再自己否掉的不算我们的错。
- 归因到动作：无理由婉拒集中在某方向 → 投放不精准；集中在「经验/年限」→ 岗位级别错位；
  A 类也被大量无理由拒且 `template_fallback` 偏多 → 问题在话术和简历，不在筛选。

判定技巧与取证步骤见 `references/round-audit.md` 第 6–8 节。

## 池子枯 / 规则卡死：定性流程与决策表

零发出、候选池看着还剩一堆时，只有两种解释：池子枯（同职能的真岗已经投完）或规则卡死（词表/阈值
把对口岗判成 C）。别用「放宽一档试试」去猜，用 `regrade` 只读回放定性：

```bash
cd ~/.boss-hunt && python3 <skill>/scripts/boss_hunt.py --json regrade                 # 现状
python3 <skill>/scripts/boss_hunt.py --json regrade --alt-config /tmp/alt-词表.json    # 每次只动一处
```

看四个数：`matrix.stored_to_current`（旧缓存按新规则重判的迁移）、`jd.grades` / `jd.causes`、
`diagnosis.verdict`、以及漏斗里的 `fresh_pool` 与 `open_role_matched`。

**一次只动一个维度**，否则没法归因：

| 只放开什么 | 说明 |
|--|--|
| `tracks.*.min_hits` 降 1 | 测「终判门槛是否挡掉了够格的岗」 |
| `jd_signals` 加同义词 | 测「词表是否覆盖不到 JD 的写法」（最常见） |
| `filters.text_block` 去掉争议红线 | 测「红线词是否与目标行业天然冲突」 |

读数方式：某维度跑出来 `C→A/B` 为 0，说明它不是瓶颈，别再拿它当答案；≥5 条才值得动。
三样一起放宽得到的 `both` 不能当结论——它只能说明「有东西在挡」，分不清是谁。

**拆开跑完还要逐条读那批 `no_signal` 的标题 + JD。** 若它们多是家具/医疗/外贸/酒店这类传统渠道
销售，问题在搜词与赛道，不在判级词表；加同义词只会把这批噪声放进来（实测「家具渠道经理」靠
「到店」、「酒店渠道经理」靠「连锁」命中）。同义词只挑高区分度业务词（连锁餐饮 / 连锁门店 /
加盟拓展 / 到店 / 开城），并同步把该 track 的 `min_hits` 抬到 2：同一池实测「只加词 → 10 条且混噪声」
「加词 + `B.min_hits=2` → 4 条且都对口」。单字泛词（渠道 / 销售 / 客户 / 连锁）进 `jd_signals`
等于把 B 变垃圾桶。`near_miss` 小也不能证明「规则不紧」——它只含「差 1 个命中」，零命中的
`no_signal`（实测占绝大多数）根本不在里面。

**诊断命令自身的误报**（别拿它当证据去删配置）：

- `validate` 的「零产出关键词」：分母若按 `open` 算，会把「没有缓存 JD、判不出等级」和「该词的
  A/B 已经发出去」两类词误判成零产出。正确口径：分母 = 已判过数（A+B+C），产出 = 该来源的 A+B
  再加上 `sent` 与 `b_pool` 里的同来源岗位。
- 「关键词与 roles 无交集」只能依据 `grading.roles`：判级只读它，`tracks.*.roles` 不参与判级，
  并进来会漏报；方向词（出海/北美/驻外）命中不了 roles，应改成「方向+职能」组合，不是塞进 roles。
- 诊断函数（`open_pool` 一类）要与真实候选口径对齐：`scoring.min_score` 过滤、`b_pool` 里已不在
  快照的岗位会被 `do_send` 补回、`checked_jobs` 当天写入会改变同一天的 open 数。
- `grades --by-src` 全 0 行会按字母序排到前面（中文 src 在 ASCII 之后），不是命令坏了；
  看合计或过滤 `open>0`。

**动词表优先于阈值**：`min_hits` 只在终判生效，粗标阶段就没进候选的岗位轮不到它；
扩同义词不降门槛、不动红线，风控上零代价，是唯一可以先做的一档。红线词要不要撤必须用户拍板。

**漏斗统计口径的偏差方向**（读 verdict 前先知道它偏哪边）：`fresh_pool` 偏乐观——没有缓存 JD 的
岗位也算可投、`load_jobs` 会合并历史快照（含可能已下线的岗）、也没排掉 `checked_jobs` 终态；
这种口径算出来只有 1，说明池子是真的干了。`legacy` 条目是旧代码判的等级，迁移矩阵混着代码变动与
规则变动两种影响，不能当纯规则效果读。`near_miss` 只统计「差 1 个命中」和「只踩 1 条红线」，
**零命中的 no_signal 在 near_miss 里看不到**——所以 near_miss 小并不等于「规则不紧」。

**`fresh_pool` / `open_role_matched` 不含「被同 HR 已投挡掉」的岗位**，所以 `verdict=pool_dry` 只能说明
「按现有去重规则没得投」，不能说明「没有对口岗」。定性之后必须再算一次：
`[j for j in jobs if "%s|%s" % (j["brandName"], j["bossName"]) in contacts and jid not in sent and judge(j) == pass]`，
并按平台侧品牌过滤一遍。实测同一份数据：regrade 说 35 个 open 全 C、fresh_pool=1，
而被同 HR 挡掉且 `judge==pass` 的有 248 个，其中 6 个是 20-50K 的平台侧主管岗 —— 两条结论
同时成立，放行规则不同而已。汇报顺序：先说「规则内能投的剩几个」，再说「被去重挡住的有几个、值不值得放」，
不要让用户以为池子真的空了。

## 同 HR 冷却窗口（2026-10-28）

`filters.same_hr_window_days` 仅控制候选过滤：缺省或 `null` 保持同一 `品牌|HR` 永久跳过；
`0` 关闭同 HR 冷却（仍拦住已投 jobId）；正数 N 表示距最近一次真实发送至少 N × 86400 秒才放行。
权威时间只取 `send_ledger.jsonl` 中 `status == "sent"` 的行，优先 `ts_epoch`，解析失败回退 `ts`；
不从缺少 HR 的 `state.sent` 猜时间。ledger 存在但该 HR 无有效 sent 时间时放行；
ledger 缺失或不可读时，正数窗口保守保持旧行为，`0` 仍放行。坏行跳过，解析结果仅在命令/单次 tick 内存缓存。
`candidates()` 与 `open_pool()` 共用过滤规则；放行项的候选 `flags` 标记 `same_hr_window_pass`，
窗口内仍为 `skip_same_hr`，岗位已投、judge 拒绝等其他条件仍生效。判级和发送路径未调整，
发送阶段现有守卫仍可能拦住候选，候选放行不代表实际发送。

风险：同一 HR 多岗时可能出现连续两次招呼；窗口只参照上次真实发送，不为同批候选预占时间。
回滚删除该配置项（或设 `null`），无需改 ledger 或 contacts。
`tick --dry-run --json` 的 `budget` 改为对象：`limit` 保留原数字预算，
`same_hr_window_days` 为配置值（未配置为 `null`）；实际 `tick --json` 的 `budget` 同样携带窗口值。

## 样本量先算再报

报「分方向回复率 / 拒绝率」之前先算 `日回复量 × 天数 ÷ 方向数`。每方向不足约 10 条时，
只报绝对数和话术质量，不要拿比例下结论 —— 否则「某个方向 0/3」会被当成方向错误的铁证。

## 换行业 / 换用户时改哪里

只改配置，不改代码：

| 要定的东西 | 配置位置 | 怎么定 |
|--|--|--|
| 目标职能词 | `grading.roles` | 问用户「你干的那类岗位，标题里通常写什么」 |
| 两侧判据 | `grading.tracks.{A,B}.industries/brands/jd_signals` | 各找 2–3 段真实 JD 提炼动词与业务词 |
| 分不清时归哪边 | `grading.unknown_side` | 默认 B（宁少不滥） |
| 比例 | `sending.grade_quota` | 先按 7:3 起，两周后按拒绝率调 |
| 节奏 | `schedule.*_windows` | 扫描窗口放少（3 个），回消息和总结各自独立 |

上线前用 `grade --jd-file` 拿一段平台侧 JD 和一段品牌侧 JD 做正负例校验：判反了就说明
词表错了，这一步不真投递、不开浏览器，是给别人配置时唯一必须做的验证。
